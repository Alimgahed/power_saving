## Design system and visual consistency

A shared Material 3 theme, Arabic Almarai font selection, color/dimension tokens, app scaffolds, cards, buttons, form fields, empty states and shimmer components exist. Several screens use them successfully. Other screens hardcode gradients, blue borders, white backgrounds, text sizes and bespoke button styling; CustomTextFormField overrides theme values. This is evidence of inconsistent implementation sources, not a measured contrast failure.

AppScaffold accepts desktopHeader but never renders it; it always chooses mobileAppBar/default AppBar. ResponsiveWrapper has no consumer found. Home owns separate breakpoint logic (450/750/1200, 500/900/1400 and others), while CRUD forms commonly use 600. Different breakpoints are not inherently wrong, but a documented shared layout policy would make behavior easier to maintain. EnterpriseSidebar exists, but source inventory alone does not establish its visibility on every desktop screen.

The app configures only lightTheme in main. A darkTheme implementation exists but is not connected as an app dark theme. Do not report dark-mode contrast as tested or dark mode as shipped. Arabic localization delegates and explicit RTL wrappers exist; most visible strings are hardcoded Arabic, and there is no complete translation catalog. An English supported-locale declaration does not establish an English product experience.

## User scenarios and improvements

| Scenario | Current problem / risk | Recommended experience |
|---|---|---|
| Clerk creates a bill from history | Add Bill navigates to an absent route (UX-01). | Open meter selection and continue to the existing billing flow; maintain a clear return path. |
| Clerk corrects a meter factor or rounding last | Derived total can remain stale (DATA-02/03). | Immediate recalculation, transparent formula and submit-time consistency checks. |
| Operator searches operational technology bills | Text edit does not update results (UX-02). | Debounced results and explicit no-result/reset state. |
| Analyst enters planning assumptions while cached data refreshes | User input can disappear (DATA-04). | Preserve dirty draft fields; indicate updated reference ranges without replacing entered values. |
| Analyst exports a filtered report | Count reflects the unfiltered dataset (UX-05); failed rows do not leave a completeness flag. | Include active filters, exported count and completeness warning in print. |
| Administrator switches accounts on a shared workstation | Prior-session caches can render before fresh authorization (SEC-04). | Clear/scoped session data, consistent sign-out and validated startup. |
| User retries after a slow/failed analysis | Loading can persist indefinitely (REL-01). | Distinct loading, empty and error views with a retry action and retained selection. |
| Native user prints a report | Platform stub silently does nothing (UX-06). | Implement export or visibly explain platform capability with an alternative. |
| User changes filters then refreshes | Some refresh methods reset filters; stale background completion may replace newer query. | Define whether refresh preserves filters, show freshness and reject obsolete responses. |
| User finishes a simple successful save | showSuccessToast is a blocking modal requiring confirmation. | Use a nonblocking success status for routine saves; reserve modal confirmation for consequential choices. |

## Accessibility and responsive validation backlog

- **Keyboard and assistive technology:** AccessibleFocusWrapper supplies semantics/focus styling but no explicit key activation handler, and has no usage found. Several icon buttons, such as technology-bill search/close/back, lack tooltips. Verify accessible names, focus order, Enter/Space activation, error announcement and dialog focus return on actual rendered trees. Standard Flutter buttons may already supply useful semantics; absence of custom Semantics is not proof of inaccessibility.
- **Text scaling and overflow:** fixed-aspect technology-bill cards, fixed-height table rows, large billing dialog Rows and long dashboard labels need device checks. Verify 320/375/600/750/1200 widths, landscape and enlarged text. Do not assert overflow without rendering.
- **Contrast and color:** measure actual text/control colors over gradients in light mode and every enabled interaction state. Report colors alone should not encode paid/error/threshold status; text/status labels already exist in several places and must be preserved.
- **Forms:** shared required-only validation and ignored custom validator hook (UX-07) need consistent field-level domain rules. Ensure decimal input, Arabic numerals/locales, ranges, negative-value policy, password manager/paste, inline errors and duplicate-submit prevention are intentional.
- **Motion:** KPI count and skeleton animations do not visibly consult reduced-motion preference in their implementation; verify platform behavior and offer a reduced-motion path.
- **Charts/reports:** verify textual summaries, units and accessible alternatives. Home uses kg/kilowatt-style labels while branch reports label chemical values in grams and electricity in watts; the backend units are unspecified, so confirm measurement contracts before changing labels or conversion.

Visual hierarchy, density, spacing, font rendering, clipped content, touch-target dimensions, screen-reader behavior and actual task completion time remain NOT VERIFIED. A source-only audit cannot fairly score their visual quality.
